## 2. 核心业务规则（铁律，碰了就是 Bug）

### 2.1 状态机（6 态，2026-07-02 确认）

```
新预约(pending_confirm)
  ↓ 工作人员确认
已预约(confirmed)
  ↓ 顾客扫码签到
  ├─ "现在开始体验吗？" → 是 → 体验中(in_experience) → 保存体验参数 → 自动 已体验(completed)
  └─ "现在开始体验吗？" → 否 → 已到店(visited)
                                                                    ↓ 工作人员手动
                                                              体验中(in_experience)

任意已预约状态 → 已取消(cancelled)（仅从 confirmed 可取消）
```

**禁止**：
- `visited` / `in_experience` / `completed` 互相跳跃
- 从 `pending_confirm` 直接到 `visited`（必须先 confirm）
- 取消后状态复活

### 2.2 状态-UI 映射（detail 页，6 态）

| 区块 | pending_confirm | confirmed | visited | in_experience | completed |
|------|-----------------|-----------|---------|---------------|-----------|
| 体验参数记录-编辑 | 隐藏 | 隐藏 | 隐藏 | 显示全部 | 显示全部 |
| 照片对比 | 隐藏 | 隐藏 | 隐藏 | 显示+上传 | 显示全部 |
| 回访反馈 | 隐藏 | 隐藏 | 隐藏 | 隐藏 | 显示(只读) |
| 跟进记录 | 显示 | 显示 | 显示 | 显示 | 显示 |
| 状态切换按钮 | →确认 | →已到店 / →已取消 | →体验中 | (自动→已体验) | - |

**关键约束**（全局）：
- 所有 `visited || completed` 判断必须改为 `visited || in_experience || completed`
- 所有 `STATUS_MAP` 必须含 6 态
- 所有 `.status-*` CSS 必须含 `.status-in_experience`

### 2.3 签到规则

| 项 | 规则 |
|----|------|
| 入口 | 顾客扫门店码 → `pages/checkin/guest/guest` |
| 匹配 | 手机号匹配今日 booking |
| 自动补全 | 从历史预约记录自动补全：姓名/性别/年龄/身份证（`_fillFromHistory`） |
| 知情同意书 | 9 个章节直接平铺，不分段展开/收起 |
| 不显示 | 进度条、"已自动补全"标签、顶部提示语 |
| 签署行 | 签署人=``，签署日期=``，为空回退 `________________` |
| 摄影授权 | 两个复选框（个人存档 / 匿名宣传） |
| 代约 | 不允许（openId 自动匹配） |
| 弹窗 | 签到成功后弹"现在开始体验吗？" |

## 4. 数据库安全规则（基于实际代码访问方式）

当前架构大部分操作是**前端直接访问** `wx.cloud.database()`，不走云函数。权限必须匹配代码：

| 集合 | 权限 | 原因 |
|------|------|------|
| `bookings` | **所有用户可读写** | 操作师需改顾客创建的预约状态/体验参数/同意书 |
| `admins` | **所有用户可读写** | managers.js 前端直接增删管理员 |
| `users` | 所有用户可读，仅创建者可写 | 操作师 getAllUsers 读全部，访客写自己的 |
| `feedbacks` | 所有用户可读，仅创建者可写 | 操作师读全部问卷，顾客写自己的 |
| `sms_codes` | 仅创建者可读写 | 仅云函数访问，前端不碰 |

**无独立 consents 集合**，同意书数据存在 `bookings` 内。

**导出功能**：`exportCSV` 从内存 `globalData.bookings` 导出，不直接查数据库，权限不影响导出。

## 5. UI 配色铁律（2026-06-30 固化，碰了就是 Bug）

### 5.1 全局原则

| 原则 | 说明 |
|------|------|
| 正文文字一律黑/灰色 | 黑色权重高（#1F2937 / #374151），灰色辅助（#6B7280 / #9CA3AF） |
| 紫色仅在按钮/标签/选中态 | #3B0764 底白字 或 #EDE9FE 底紫字 |
| 大色块底色一律灰色 | #F3F4F6 |
| 所有页面导航栏透明 | `navigationStyle:custom`，与首屏大图融合 |
| 导航栏标题在 nav-bar 组件中显示 | 页面内不重复写标题 |
| 按钮圆角 | 一律 `16rpx`，禁止用 `var(--radius-full)` / `9999rpx` |

### 5.2 颜色色板

| 用途 | 颜色 |
|------|------|
| 正文文字 | #1F2937（黑）|
| 辅助文字 | #6B7280 / #9CA3AF（灰）|
| 按钮底 | #3B0764（紫）或 #F3F4F6（灰）|
| 按钮字 | 紫底=白字，灰底=紫字 |
| 标签底 | #EDE9FE（淡紫）/ #F3F4F6（灰）|
| 标签字 | #3B0764（紫）/ #6B7280（灰）|
| 大色块底 | #F3F4F6（灰）|

### 5.3 状态标签四色
- 待确认 = 紫
- 已确认 = 绿
- 成交 = 灰
- 流失 = 红

### 5.4 页面例外
- `pages/index/index` = 全屏 Hero，无 nav-bar 组件，不动
- `pages/mine/mine` = 登录按钮保留紫色渐变，其它文字黑灰

## 16. 改动代码铁律

> 来自原开发者多次被 Lisa 反馈后总结：

1. **改业务相关代码前**，必须先完整阅读现状，不能凭记忆瞎改
2. **改完状态/业务逻辑后**，必须逐状态自查（6 态都要走一遍）
3. **页面改完同步生成 HTML 预览**，覆盖 `preview/` 目录对应文件
4. **禁止用 `wx:else` 兜底多状态分支**，每个状态必须显式匹配
5. **问卷**仅在触发时间窗口内且用户未填写时显示；已填即隐藏
